## 2. Short summary of what changed

This work completed Phase 7 by implementing the bounded offline ZiFS repair
boundary, integrating it into host and persistent-QEMU acceptance, correcting
recovery copy ordering, and auditing every Phase 7 exit criterion.

The new Windows-host zifsrepair.exe separates read-only planning from exclusive
apply. It repairs only uniquely provable superblock redundancy,
journal-header redundancy, transaction-free interrupted-mount state, or a safe
combination. Exact old and replacement block images are bound to a SHA-256
review token. Apply replans, verifies the token and current bytes, flushes after
every block, and requires a complete clean fixed-point inspection. Unknown or
ambiguous corruption, active transactions, security damage, namespace damage,
extent errors, and allocation leaks are refused.

The read-only inspector and repair command boundaries now accept genuine
Windows UTF-16 paths containing spaces and non-ASCII characters. The host gate
is 34 groups and 3,045 assertions. The ZiFS matrix is 32 QEMU/EDK2 boots and
now includes offline repair of a persistent GPT image followed by a direct
ZiFS boot without recovery markers. All final required gates pass.

## 16. What is intentionally not implemented yet

General filesystem reconstruction is intentionally absent because guessing
through corruption would violate fail-closed policy. The repair tool does not
replay/roll back transactions, regenerate ACLs, infer names, reclaim leaks, or
salvage data.

Also intentionally absent at this stage are production storage breadth,
dynamic drivers, SMP, concurrent user scheduling, a complete C runtime or
compiler, GUI, network, audio, power, packages, updates, Secure Boot, BIOS,
ARM64, RISC-V, and daily-use applications.

## 18. Current boot status

The import-free AMD64 PE32+ kernel boots through EDK2 and Limine revision six,
enters the Microsoft x64 environment, owns its descriptor/interrupt tables,
memory, x2APIC timer, and protected address spaces, mounts the frozen-GUID ZiFS
partition through QEMU NVMe/GPT, loads core PE files from ZiFS, launches the
service/session/user-mode Luma slice, exercises pre-emption, and cleanly
unmounts. Serial and framebuffer output work. Negative fault and storage boots
fail closed as designed. The module path is explicit recovery only.

## 19. Current ZiFS status

ZiFS 0.1 is a real little-endian 4 KiB-block filesystem with checksummed,
redundant and journalled metadata, exact validated UTF-8 names, multi-block
directories, extents, durable ACL references, direct partition I/O, bounded
mutation, barriers, crash recovery, lifecycle state, read-only inspection, and
bounded offline repair.

Limits remain: one synchronous writer, 28 staged home images, 24 data blocks
per create/write request, four inline extents, 256 directory blocks,
shrink-only truncate, regular-file-only delete, no sparse files, no cache, no
directory reclamation, and no general salvage. ZiFS remains experimental and
must not hold irreplaceable data.

## 20. Current scheduler status

Implemented are 32 FIFO priority queues, bitmap selection, affinity fields,
quantum/boost/decay hooks, idle representation, dispatcher locking, waits,
isolated x64 context switching, a calibrated 100 Hz x2APIC tick, and repeated
uniprocessor kernel-thread pre-emption. SMP/AP bring-up, IPIs, cross-CPU
balancing, concurrent user-thread scheduling, and mature realtime/starvation
policy remain future work.

## 21. Current ACL and security status

## 29. Known limitations

- The repair utility is offline, Windows-host-only, bounded, and deliberately
  incapable of general reconstruction or data salvage.
- ZiFS mutation and storage support retain the bounds listed in section 19.
- Only one polling QEMU NVMe controller and namespace are verified.
- Userland and security use trusted bootstrap tokens, not authenticated
  persistent identities.
- User processes execute through bounded synchronous paths rather than a
  general concurrent scheduler.
- Many platform, driver, desktop, application, installer, update, and
  multi-architecture facilities remain incomplete.
- The workspace has no Git metadata, so commit-based provenance is unavailable.

## 33. Architectural decisions that must not be changed

- Product and subsystem names remain Zizium, ZiFS, Luma, ZIA, Zx, ZiCRT, ZCC,
  zpkg, ZiUI, Zin, and ZinRT.
- Zizium-owned work remains GPL-3.0-or-later; third-party licences remain
  separate.
- x86-64/UEFI/Limine is current; a future boot manager supplies ZiBootContext.
  ARM64, RISC-V, and BIOS are later.
- PE/COFF is native; ELF is not. The kernel remains modular monolithic and
  NT-inspired without claiming Windows compatibility.
- Microsoft x64 is the C ABI. Limine System V remains isolated. Syscalls use
  RAX, then R10, RDX, R8, and R9.
- ZiFS is the root/system filesystem; FAT32 is ESP-only. Its GPT type GUID is
  9ef9e22a-3719-44d4-89af-de9cc7b6b255.
- Native paths use drive roots/backslashes, preserve spaces, and compare exact
  validated UTF-8 sequences case-sensitively without implicit normalisation.
- Ordinary C main remains first-class. ZiMain and mandatory zizium.h are
  forbidden.
- ACLs and tokens remain default deny with no administrator or SYSTEM bypass.
- Scheduler priorities remain 0, 1–15, and 16–31. Display scale remains
  rational and per output. Assembly remains restricted to essential
  architecture boundaries.
- British English and the calm #6496e6/#d1ecfc visual identity remain.
- Placeholders are never described as runnable without a real path.
- ZiFS remains write-ahead and old-or-new after crash. Released blocks cannot
  be reused before durable checkpoint/recovery.
- zifsinspect remains non-mutating. zifsrepair remains separate, explicit,
  reviewed, narrowly enumerated, and fail-closed.
- Durable identities and credentials must live on ZiFS and use reviewed
  cryptography; no alternate security database or custom password primitive is
  permitted.
